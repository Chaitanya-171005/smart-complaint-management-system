## Implemented in this contribution

ComplaintForm validates required category, location, title, description and
indicated priority. Sub-category is optional. Text is stripped before validation.
SRS Appendix B-2 limits: title 120, description 20–2000, sub-category 50;
category name 50; location block 20, optional floor 10, room/area 30.
The description minimum counts visible letters, numbers, punctuation and symbols;
spaces, controls, format characters and standalone combining marks do not count.
This conservative count is not a Unicode grapheme counter. Multiline descriptions
are allowed. Title and sub-category reject Unicode Cc/Cf controls and formatting
characters, plus Zl/Zp line/paragraph separators, before whitespace stripping.

Priority remains required: REQ-CMP-01 explicitly lists four mandatory fields but
Appendix B-2's "Title / description / priority" row marks all three "Yes"; UC-03
also has the user enter priority. This implementation follows that appendix.
initial=MEDIUM is only a display default, never a fallback for a missing POST value.
ComplaintForm.Priority currently matches B17 PR #53's four values/labels. A contract
test asserts equality when routing.models.Priority exists and explicitly skips
while that unmerged dependency is absent. Replace the local constants with the
shared enum when #53 integrates; no other priority policy is introduced here.

Selectors accept only active, known server-supplied records. Categories and
locations are refreshed when constructing each request's form; POST data cannot
introduce a new reference record, role, submitter, department or state.
Bound forms preserve safe values and Django escapes HTML on rendering.
Only active reference records are validated. Invalid active records are omitted
from selectors and logged by record kind, without echoing raw master data. Neither
record with a duplicate active key is offered. An empty selector cannot validate;
the future view must show a clear configuration-unavailable message if none remain.

build_complaint_form uses accounts.permissions.can_submit_complaint and the shared
B04 enforcement helper, accepting only active,
authenticated Complainants. Call it with the current request.user.
Permission is enforced before either reference collection is iterated, including
when malformed options are supplied by an adapter.
The HTTP view remains responsible for login redirection and CSRF middleware.

## F1/F3 integration contract — proposed for owner review

F3 supplies current category records as CategoryOption(key, name, active).
F1 supplies current location records as
LocationOption(key, block, room_area, floor="", active=True).
CategoryOption.key is the stable category primary key serialized as a string
(for example str(category.pk)), never its editable display name. LocationOption.key
is F1's stable canonical location_code, the same code used by B17 RoutingRule.
B17 normalizes routing codes with strip().upper(); the F1 adapter must supply that
canonical representation here too. A renamed block/room label must retain its code.
If F1 also uses a numeric location primary key, its adapter maps that key to this
code; a display label or an invented code must never substitute for the mapping.
This is an integration contract for owner confirmation; the database adapters are
still pending. Keys must be unique nonempty strings. Pass both collections to the form;
never obtain those collections from the submitted POST body.

cleaned_data["category"] and ["location"] are the selected canonical option
objects. Other cleaned fields are sub_category, title, description and priority.
Priority is the user's indication. F3 must derive effective priority as the higher
of the indicated value and the current category minimum, using the order
LOW < MEDIUM < HIGH < CRITICAL, then derive the due time from that effective value.
The eventual intake transaction must re-read the current category minimum and
never trust effective priority or a due time supplied in POST. This PR does not
implement routing, due dates or persistence.
The adapters do not prescribe migrations. B17 currently allows category names up
to 100 characters; B07 follows the SRS limit of 50. Longer names are logged and
omitted rather than displayed as unsubmitable options; owners must reconcile the
schema limit before final acceptance.
All option values in the tests are clearly synthetic.

F1/F3 owners must review this boundary before connecting their database adapters.
Recheck current master data inside the final intake transaction to handle
deactivation between validation and persistence.
