# B28 — notification list and read state (issue #38, TC-11 / TC-13)

B26's durable recipient notices are reused. Nullable read_at (migration
0005_b28_notification_read_at) makes existing/new notices initially unread.
No event or email-delivery state changes when a recipient reads a notice.

- GET/HEAD /complaints/notifications/ lists newest first by created_at and PK,
  with 25-item pagination. It never changes read state.
- POST /complaints/notifications/<notice_id>/read/ requires login and CSRF.
  Only the intended recipient with current F1 complaint access can mark it read;
  missing/inaccessible notices return 404. First read_at wins; repeats are safe.
- Header counts on role home and workflow pages use the same current authorized
  notice scope. Counts are server rendered and refreshed by page navigation or
  the successful POST redirect; there is no polling/live-push promise.
- Read updates are atomic with an actor lock and conditional update. Counts are
  derived from authorized rows with read_at IS NULL, not a separate cached total.
- Pages are private/no-store. The list displays timestamp, event kind, public
  complaint ID/status and read state only. No complaint body, reporter, history
  remarks, reference/digest, attachments or SMTP diagnostics are projected.

Apply the normal Django migrations at deployment before serving this UI; no
application database migration is executed by implementation/check commands.
PR #68's independent migration graph still needs coordination when integrated,
as already documented for B26. No new external service or reference capability
is introduced.
