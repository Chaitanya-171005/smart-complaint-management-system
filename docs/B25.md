# B25 — scheduled automatic closure (issue #35, TC-10)

## D05 proposed policy — pending team approval

This implements the requested proposal, not a formally approved campus policy:
`COMPLAINT_AUTO_CLOSE_DAYS` defaults to 7 elapsed days. Eligible at exact equality:
`now >= resolved_at + duration`. Configuration accepts positive whole days
(1–36500, a technical timedelta bound); invalid settings fail without writes.
Only still-RESOLVED rows with a non-null expired resolved_at qualify.

The first valid transaction wins the same complaint row lock used by B23/B24.
Account feedback still checks its opaque revision. Feedback accepted first is
never overwritten: REOPENED/CLOSED rows are skipped, and maximum-reopen
RESOLVED -> RESOLVED feedback escalations since the current resolution timestamp
are held for Head review, not auto-closed. That hold has no automatic release;
a later dedicated Head workflow/policy remains outside B25. A later fresh
resolution timestamp begins a new resolution period. These feedback semantics
also require D05 review. No F3 due timestamps, overdue flags or assignments change.

Each closure writes closed_at, CLOSED, SYSTEM STATUS_CHANGED history with static
`Automatic closure; resolution unconfirmed.` remarks, and existing B26 CLOSED
notices/email jobs in one transaction. No rating or owner confirmation is
invented. Anonymous closure uses the same static marker with no reporter data.
No new schema is needed. B20's internal writer is shared after scheduler policy
validation; account APIs still require real owner authorization and cannot pass
a system flag. SMTP remains the B27 worker's responsibility.

`run_auto_close(now=..., limit=100)` uses a bounded candidate scan, with each
complaint locked and eligibility rechecked in its own transaction. Already
completed work is durable if a later item fails; rerunning is safe. Worker
failures use sanitized command diagnostics. Repeated/overlapping runs do not
create duplicate history or notices. Deployment-specific DB locking still
requires operational verification.

## Deployment example — install only after D05 approval

Set `COMPLAINT_AUTO_CLOSE_DAYS=7` in the protected application environment/.env.
Use the same runtime environment, persistent database and timezone-aware Django
settings as the web process. Preview/review the proposed policy before enabling
the schedule. Run manually with:

```
/srv/scms/.venv/bin/python manage.py auto_close_complaints --limit 100
```

A cron example is in deploy/auto-close.cron.example. Adjust paths/user and batch
size for deployment volume. Cadence determines processing lag after the exact
eligibility deadline. Monitor nonzero exits and rerun failed batches. Keep the
separate `deliver_notifications` schedule active for durable email delivery.
No schedule is installed by this change.
