# B18: Scheduled escalation

`run_escalation(now=None, notify=None)` records a run and processes eligible
past-due complaints in individual transactions. The `run_escalation` management
command runs the scheduled pass. F3 calls the optional F4 durable history
publisher inside the complaint transaction; publication failures roll it back.
Without F4, only history is durable and no notification job is created.
Head notification delivery belongs to F4's separate worker. The legacy optional
post-commit notification hook defaults to a no-op and is not a durable queue.

When `run_escalation()` is called inside an outer transaction, notification
callbacks run after the outer commit, after the run has been finalized. A
notification failure then cannot be reflected in the run's error text. The
management command runs without an outer transaction.

A failed complaint transaction is rolled back independently; other eligible
complaints continue and successful transactions remain committed. Any complaint
processing failure marks the run FAILED, with a finished timestamp and counters;
the management command returns a nonzero exit status. Error text is generic so
it does not expose complaint data or exception details. A later run can retry
eligible complaints that failed.

An interruption marks the run FAILED and is re-raised. The interrupted complaint
is counted as failed if its transaction rolled back; an interruption in an
on-commit notification is counted as escalated because its transaction already
committed. Finalization errors do not replace the original interruption. A run
inside an outer transaction is still subject to that transaction's rollback.
Issue #26 remains open for deployment and F4 acceptance.

## Deployment scheduling

Use the existing host cron architecture, not a second loop/Celery scheduler.
`deploy/escalation.cron.example` provides mutually exclusive Docker and native
examples. It is not installed automatically. The one-minute example is polling
cadence, not an SLA duration; escalation eligibility still uses DB policy.

The Compose `scheduled-task` profile is an opt-in one-shot app-image service
sharing the web environment, database and private-evidence volume. It overrides
the web entrypoint to avoid repeated migrations, disables the HTTP healthcheck,
has no published ports or restart loop, and runs as the image's unprivileged user.
After the normal web deployment has successfully migrated its database, a manual
pass is `docker compose --env-file .env.docker --profile scheduled run --rm
--no-deps scheduled-task run_escalation` (enter as one command). Cron must use
absolute paths and a runtime user authorized to access the protected env file.
`--no-deps` ensures that a missing DB fails the task instead of starting services.
Only validate with `docker compose --profile scheduled config --quiet` during
review; do not print resolved credentials or start jobs on a reserved environment.

Each invocation exits; cron retries on the next tick. Monitor nonzero exit status,
generic aggregate output and RUNNING/FAILED run records. Repeated/concurrent
invocations rely on complaint locks and eligibility rechecks, not a host-local
lock that would fail across hosts. Verify actual PostgreSQL concurrency before
production rollout. Hard process termination can leave a RUNNING audit record;
the next invocation retries eligible complaints, but does not rewrite that record
or recreate post-commit legacy callbacks. Do not delete immutable history.

F4 `deliver_notifications --limit 100` is shown only as a commented future cron
entry. Its worker owns recipient reauthorization, bounded retries and expired
claims; SMTP failure cannot undo an already committed complaint transition.
No F4 models or worker are installed by this candidate. Auto-close is unavailable
in this base; PR #78 calls D05 PROPOSED. Do not activate its deadline/default or
schedule until lifecycle implementation and policy are accepted. No auto-close
deadline is introduced here. See docs/SMTP.md before any controlled delivery.
