# B15: Department queue and allocation

`department_queue(user, department)` returns the authorized, scoped queue;
`department_queue_page(user, department, page_number=1)` paginates it at 25.
The queue includes ASSIGNED, IN_PROGRESS and REOPENED complaints. Escalated
complaints come first, followed by priority CRITICAL, HIGH, MEDIUM, LOW, then
submission time and primary key ascending.

`allocate_complaint(*, actor, complaint_id, assignee, expected_assignee_id,
reason="")` changes only the assignee, recording the action atomically. First
allocation needs no reason. Reassignment requires a different assignee and a
trimmed reason of 1–500 characters. Errors include `not_allocatable`,
`modified_record`, `reason_required`, `reason_too_long` and `same_assignee`.

The additive history migration adds nullable actor and assignee account references.
Anonymous history clears both references; a database constraint enforces this.

## Assumptions to confirm

- ASSIGNED, IN_PROGRESS and REOPENED as queue and allocatable statuses are an assumption from the SRS.
- The history-model change needs Tanmay's (F4) review.
- Assignee behaviour after reopen is undefined (D04); no behaviour is invented here.

## HTTP and coverage

The queue page is `GET /routing/queue/`, available to active department heads and staff for their own department. The assignment form posts to `/complaints/<id>/assign/`; the endpoint requires a department head and CSRF protection. It accepts `assignee`, `expected_assignee` (empty for initial allocation), and `reason`. Successful assignments redirect to the queue; validation failures return 400. Unauthorized access follows the existing role and allocation permissions.

Service coverage is in `routing/test_queue.py` and `routing/test_allocation.py`; HTTP coverage is in `routing/test_b15_http.py`. Tests cover role and department restrictions, validation, CSRF, status and stale checks, rollback, exact history, queue pagination and competing initial and reassignment requests using separate connections. The database configuration uses SQLite IMMEDIATE transactions; row locking semantics on other database backends have not been independently tested.
