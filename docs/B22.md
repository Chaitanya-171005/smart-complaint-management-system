# B22 progress, resolution and private evidence

Issue #32; REQ-LIFE-03, REQ-SEC-05, BR-01; TC-02 / TC-05 / TC-08.
This extends the existing uncommitted B20/B21/B26/B27 work on the same branch.
No new migration or Complaint/Attachment field is needed.

## Acceptance and authority

- progress_complaint starts ASSIGNED or REOPENED work as IN_PROGRESS. F1/SRS
  §4.3 permits assigned same-department Staff or that department's Head.
- resolve_complaint permits only active assigned same-department Staff and only
  IN_PROGRESS to RESOLVED. Admin, Head, owner, unassigned/cross-department Staff,
  anonymous users and inactive accounts cannot resolve. Current authority is
  checked before any file parsing and again after staging.
- Required proof is resolution remarks of 20–2000 trimmed characters. Evidence
  is optional under REQ-LIFE-03/B09: zero to three JPEG/PNG/PDF files per operation.
  No universal mandatory attachment rule is invented. Client MIME is ignored;
  B09 verifies actual content, filename/extension, bytes and processing limits.
- Accepted resolution writes remarks/resolved_at, RESOLVED state, RESOLUTION
  Attachment metadata, B21 history and B26 recipient notices/outbox together.
  It never sets CLOSED, closed_at, rating, reopen_count or due-time policy.
- B20 opaque revisions reject stale, replayed and concurrent actions. A lost
  acknowledgement is handled by refreshing current work status, not by creating
  another accepted resolution. Only one competing proof batch is retained.

PR #49 remains unmerged. Its compatible validate_resolution contract and six
original tests were read from the local B22 ref into previously absent files;
the helper now also enforces the SRS maximum and rejects NUL text. Neither that
branch nor its commits were changed or merged. There is one shared validator,
not a second competing implementation. The B20 generic mutation gate remains
closed for raw resolution calls; the dedicated B22 service supplies validation
before using _account_transition and _apply_locked_transition.

## Services and filesystem transaction boundary

```
progress_complaint(actor=..., complaint_id=..., expected_revision=..., remarks="")
resolve_complaint(actor=..., complaint_id=..., expected_revision=..., remarks=..., files=())
```

Use get_transition_revision with target IN_PROGRESS or RESOLVED as appropriate.
No caller-selected status, uploader, storage key, Attachment ID or callback is
accepted. The assigned resolver is the server-controlled uploader; this records
Staff authorship, not anonymous-reporter attribution. Metadata stage is always
RESOLUTION. Retained intake/earlier resolution evidence is never overwritten or
deleted. Three files is a new operation limit, not a global lifetime limit; no
append/edit endpoint exists to accumulate more files within the same operation.

Resolution must own the outermost database transaction. Nested use is refused
before parsing/staging; HTTP callers use non_atomic_requests, including with
ATOMIC_REQUESTS enabled. A preflight B20 transaction checks scope/state/revision
and remarks. B09 then validates immutable byte snapshots and stages them outside
the actual B20 transaction. The second transaction rechecks role, assignment and
the SAME revision under the aggregate lock before writing metadata/state/history.
Storage encloses that transaction so ordinary failure/commit rollback cleans only
this operation's generated files. No mail is sent on the request path.

B09 staging now includes the narrow accepted-primary-metadata protection already
developed in F2 PR #76. If a callback raises AFTER commit, accepted file bytes
are preserved instead of deleted; unknown DB state defers cleanup. Cleanup logs
use static diagnostics without exception values/tracebacks. The optional
anonymous keyword is compatible with F2 PR #71. Three existing B09 cleanup tests
now request a DB fixture because that safety check intentionally uses metadata.
This does not import/duplicate F2 storage or the full recovery implementation.

A post-commit exception can leave an accepted action with an unconfirmed HTTP
outcome. The form gives a refresh instruction; status/proof remain queryable and
the old revision cannot duplicate the action. Process death or cleanup failure
can leave private orphan files. Full writer leases/fsync/reconciliation belong
to PR #76/Q05; this branch makes no standalone crash-atomic DB/filesystem claim.
Database/file-storage deployment durability and PostgreSQL still require checks.

## Web interfaces and privacy

| Route | Methods | Behavior |
| --- | --- | --- |
| /complaints/<id>/progress/ | GET / POST | Authorized form; POST commences work |
| /complaints/<id>/resolve/ | GET / POST | Assigned Staff form; POST submits complete optional evidence batch |
| /complaints/<id>/work/ | GET / HEAD | Current authorized state, remarks, protected resolution-proof links |

Forms require authenticated current-role access, CSRF and the revision; GET/HEAD
never mutate work. Unsupported fields/files are refused rather than used to
assign state/uploader/storage keys. Successful POST redirects to current status.
Invalid input returns 400, stale/inapplicable actions 409, scope/permission
denials retain F1 404/403, and uncertain operational outcomes return sanitized
503 with a refresh instruction. Templates escape remarks and filenames are not
rendered. The work page is a narrow action receipt, not a replacement B19 list,
full intake/history detail, B28 notification UI or B23 feedback screen.

All proof bytes use PrivateEvidenceStorage and F2's existing parent-authorized
GET/HEAD downloads: generated keys, no public URL, forced attachment, nosniff,
private/no-store and sandbox headers. An anonymous reference is never accepted
as evidence authorization. The anonymous reporter stays submitted_by=None;
Staff/Head notices and mail contain only B26's minimal ID/status projection,
not remarks, file names, reference/digest or reporter/source metadata. B09 format
verification is not a malware scan or removal of all identifying pixels/text.
Keep F2's anonymous release gate disabled pending its owner/privacy acceptance.
