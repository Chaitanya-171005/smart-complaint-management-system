# B24 — resolution rejection and reopen limits (issue #34, TC-09)

`reject_resolution(actor=..., complaint_id=..., expected_revision=..., reason=...)`
uses B20's checked aggregate transaction and current F1 owner permission. Obtain
an opaque revision targeting REOPENED. Only RESOLVED work is eligible. Reasons
are trimmed, require 20–2000 characters, and reject NUL (the existing lifecycle
technical input bound). There is no caller-selected department, count or status.

The default maximum is two reopens. Below it, increment the persisted count and
use B20's writer for REOPENED state and B21 reason history/B26 department notices.
At or above it, retain RESOLVED and the count; append an ESCALATED event with
RESOLVED -> RESOLVED and the reason. B26's existing event pipeline notifies
eligible Head(s), assigned Staff and owner. This feedback escalation is distinct
from F3 overdue escalation: no overdue flags/levels, due time or assignment are
changed. It needs no new history/notification schema. Reasons remain in the
append-only history, never in notification projections. SMTP is worker-owned.

History and notices share the feedback transaction. Publication failure or an
outer rollback reverts the count/state/history/notices. Each accepted feedback
changes the history-backed revision; replaying the same action fails stale,
including at the maximum. A fresh authorized revision permits new feedback for
Head review; the maximum prevents additional reopens, not further feedback.

The owner detail links to `/complaints/<id>/reject-resolution/`. GET is read-only,
POST requires CSRF and the revision. Unsupported fields/files are refused and
successful submissions redirect to the existing owner detail. This is resolution
feedback, never the terminal REJECTED action.

## Outstanding acceptance dependencies

- D04 remains unresolved in docs/B16.md and issue #24. This implementation leaves
  stored due_at untouched and invents no SLA reset/recalculation. This is not a
  claim of approved reopen SLA behavior; F3/team policy integration and acceptance
  remain outstanding. Resolution timestamps/evidence and prior history remain
  retained, not erased. No scheduler or overdue policy is added here.
- F2 B13 reference authorization is absent, as for B23. No anonymous lookup or
  reference capability is invented; even a valid issued reference cannot act or
  gain full-record/evidence access here. Anonymous feedback needs F2 integration.
- Head review is delivered through existing durable notices. No new Head review
  screen, reassignment or automatic lifecycle decision is invented.
