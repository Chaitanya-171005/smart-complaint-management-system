## Recipient and channel contract

The SRS §5.3 specifies affected parties rather than an exhaustive recipient
matrix. The following explicit interpretation needs F2/F3 owner review:

| Successful event | In-app recipients | Email |
| --- | --- | --- |
| Submission | Originating active Complainant | Yes |
| Department assignment | Owner, department Heads, eligible assigned Staff | Yes |
| Staff allocation/reassignment | Owner, department Heads, new assigned Staff | Yes |
| Work commencement | Owner, department Heads, assigned Staff | No |
| Resolution | Owner, department Heads, assigned Staff | Yes |
| Escalation | Owner, department Heads, assigned Staff | Yes |
| Reopen | Owner, department Heads, assigned Staff | No |
| Closure (including automatic) | Owner, department Heads, assigned Staff | Yes |

Recipients must pass F1 can_view_complaint. Exclude inactive accounts, Admins,
other departments and unassigned Staff. Anonymous complaints have no owner
recipient; never infer one from session/uploader/source metadata. A missing email
does not prevent the in-app notice. All department Heads are addressed because
the schema permits more than one; no implicit arbitrary “first Head” is chosen.
No notice/email is invented for terminal rejection, outside REQ-NOT-01's list.

## Persistence and transaction boundary

Three new models: NotificationEvent (one per immutable success-history row),
Notification (unique event/recipient), EmailDelivery (one per emailed notice).
Event data contains only public ID, status, event kind and an anonymous flag;
no rendered arbitrary payload, address snapshot, actor account or source data.
Recipients are addressed accounts, not anonymous-reporter identity attribution.

record_history now calls publish_history_event within its transaction, after the
history row is saved. F2 intake's SUBMITTED/ALLOCATED rows therefore atomically
persist notices/outbox with Complaint, attachments and receipt. Replays retain
the same rows; refused operations generate no success notices. Required DB
failure propagates and rolls back the action. SMTP is never called here.

Publication locks the Complaint, and history/event plus event/recipient plus
notice/delivery uniqueness protects repeated/concurrent publication. Its key is
history.pk, not caller text, timestamps or event kind: distinct legitimate
escalations or reopens must remain distinct. Existing non-Complaint legacy
history is preserved without manufacturing a Complaint or notification.
The publisher is a trusted internal API, not a user-authorized action endpoint.
Callers still authorize/validate state and use the same transaction as B21.

get_notification and notifications_for reload the current user, enforce recipient
ownership and scope the parent complaint through F1. They add no web route or
read-state mutation; B28 UI/count/POST/CSRF work is not implemented.

## Email worker and failure boundary

Schedule `python manage.py deliver_notifications --limit 100` through E03.
The command requires the B26 migration. It claims PENDING jobs under a database
lock, commits SENDING, then calls Django's configured default MAILERS transport
outside all business transactions. A second worker cannot claim the same job.
Delivery rechecks current recipient eligibility/address before claiming. A role,
department or assignment change can suppress delivery. Revocation simultaneous
with SMTP cannot be atomic across the external relay; current checks occur at
claim time. Transport setup belongs to Q02/E03: use STARTTLS/SMTPS, a bounded
timeout and environment-owned credentials. Default Main uses console email;
no external email is sent by the tests.

Mail contains only static event wording, public ID, event status and “Anonymous”
where applicable. One addressed To recipient per message; no CC/BCC. Failure
records use a static delivery_failed code, never exception text or SMTP values.
Failure leaves accepted business data/history and all in-app notices intact.

This is a one-attempt outbox foundation, not B27 acceptance. FAILED jobs are
retained without automatic retry. SENDING after a crash represents an unknown
delivery result and is not automatically reset: SMTP cannot guarantee exactly
once, and blindly reclaiming may duplicate mail. B27 must define bounded retries,
increasing delays and recovery/ambiguous-result handling. Pending committed jobs
survive process exit even when no worker ran. Database finalization failure after
SMTP may leave SENDING; it cannot reverse the original complaint action.

## Anonymous privacy and unmerged interfaces

On Main without PR #71, the minimal ID/status/anonymous projection requires no
reporter identity. When F2 complaints.privacy is present, the service calls its
complainant_label and anonymous_summary AFTER recipient authorization and
retains only validated ID/status. Unexpected helper/dependency failures fail
closed. F2 helpers are not duplicated or copied into this branch.

No title, description, remarks, evidence, filename, full name, credential,
session, IP address, tracking reference or digest is rendered into a notice or
email. Use the same projection/authorization discipline for future #39 reports
and CSV; those consumers and staff screens are absent and not claimed complete.
Keep F2 anonymous release disabled pending the remaining #75 reviews and
deployment/privacy acceptance; this branch changes no release settings.

PR #68 already uses record_history, so allocation gets the same publication
without a second hook. Preserve its actor/assignee changes. B26 creates migration
0003_b26_notifications independently from its workflow/0003 actor migration;
when both are integrated, add an ordinary merge migration with both leaves as
dependencies. Neither existing migration is rewritten and no data reset is
needed. This branch does not include that unavailable dependency or merge a PR.

PR #70's transactional ESCALATED history produces the durable event. Its old
after-commit notify callback must NOT publish another event/send a second mail;
the default no-op is safe with the B26 writer. B20-B25 future lifecycle callers
use STATUS_CHANGED with IN_PROGRESS/REOPENED/CLOSED, or RESOLVED as documented
in B21; they must not invoke SMTP. PR #71's shared persistence also uses B21,
so anonymous intake participates without changes to its unmerged source.

integration_checks/anonymous_escalation.py replaces #71's spy-only contract with
the actual notice/outbox worker. Explicitly run it in a source tree containing
F2 anonymous + F3 escalation + B26; missing dependencies fail, never skip.
