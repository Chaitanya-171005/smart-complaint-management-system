# B08 — transactional complaint ID allocator

Owner: Atul Suresh — PES1UG24CS098. Related issue: #13; REQ-CMP-02.

## Delivered scope

This contribution adds an internal persisted yearly counter and a transaction-bound
allocator for SCMS-YYYY-NNNNNN identifiers. Allocation is tested for concurrent
connections, rollback, a fresh year, reconnection, and six-digit exhaustion.
It is an allocator foundation, not completion of B08 or an accepted complaint.

Main currently has no Complaint model and B14/B16 routing and due-time integration
are pending. This patch does not create partial complaint records or a premature
acknowledgement page. Issue #13 must remain open.

## Caller contract for B08/B10 integration

Use allocate_complaint_id(submitted_at=server_timestamp, using="default") inside
the outer intake transaction. Pass the same aware server timestamp that will be
stored as submission time, not a timestamp from POST. The year uses the project's
configured TIME_ZONE (currently UTC), independent of a user's activated timezone.
Yearly counters start at one; after 999999, allocation fails rather than emitting
a seventh digit. This yearly numbering policy is documented for team review;
the SRS prescribes the ID format but does not require a gap-free sequence.

SQLite lock mode is configured in scms/settings.py: OPTIONS uses
transaction_mode="IMMEDIATE" and timeout=20. The outer transaction reserves the
writer before any master-data reads, so the allocator does not need to run first.
The timeout lets competing transactions wait for that reservation instead of
attempting a DEFERRED read-to-write lock upgrade. Keep transactions short: do not
hold this writer reservation during slow external work. Allocation still begins
with an atomic UPDATE to serialize counter increments.
On a new-year insert conflict, an inner savepoint isolates the IntegrityError
before retrying the atomic increment. The caller must use the same database for
the counter, complaint and required history. No database-lock retry is hidden
inside this helper. If a lock timeout or another retryable transaction failure
occurs, B10 must retry the entire intake transaction, not only a fragment.

After reservation, the future transaction must recheck master data, persist the
Complaint, route it, compute priority/due time, attach validated evidence and
write required history. Required-operation failure rolls back the reservation
with those writes. A rolled-back number can be reused because it was never
acknowledged as accepted. Never reset/delete a live counter; no admin/editor or
public URL for the counter is provided.

Only display acceptance AFTER the whole transaction commits. An allocated string
is provisional until then. The future Complaint model must enforce a unique,
immutable identifier and the submitted_by/department/assignee authorization
contract. Counter allocation does not itself enforce model-field immutability,
user authorization, idempotency keys or complete B10 recovery.

## Verification

Install requirements.txt and requirements-dev.txt as described in SETUP.md, then:

    python manage.py migrate
    python -m pytest complaints/test_identifiers.py --no-cov
    python manage.py check
    python manage.py makemigrations --check --dry-run

For final evidence, commit source changes, verify git status --short is empty,
then run:

    python scripts/run_tests.py --evidence-dir docs/evidence/b08

Commit the generated B08 evidence separately. Existing E02/B07 evidence must not
be rewritten. A green module coverage gate is not feature acceptance.
Concurrency tests use eight independent connections against the project's
file-backed SQLite test database, including simultaneous first-use of a year.
The read-before-allocation regression covers both an absent and existing counter:
each of eight workers starts three transactions, reads active Department data
first, then allocates. All 24 allocations must succeed with distinct IDs and the
expected persisted counter. Database exceptions propagate; the test has no retries.
Its start barrier is outside the atomic block because IMMEDIATE serializes entry
to outer transactions. A barrier inside would prevent the lock holder finishing.
Other database engines have not been verified by this contribution.

## Open integration decisions

TIME_ZONE remains UTC pending team agreement on the campus calendar. Thus 00:30
Asia/Kolkata on 1 January is still 31 December UTC and uses the previous UTC year.
The existing timezone test verifies that the configured project zone governs the
identifier year. Changing the global timezone affects other modules and is not
silently included in this locking fix.

The counter migration is complaints/0001_initial.py. If another unmerged PR adds
an initial complaints migration, the second integration must reconcile the
migration names and dependencies and rerun migration checks before merging.

## Remaining acceptance criteria

- Complaint model, unique/immutable persisted complaint ID and metadata.
- SUBMITTED then department-routed ASSIGNED history via F3/F4 integration.
- Acknowledgement only after fully successful intake.
- Real routing/storage/history failure injection and idempotent retries in B10.
- Final end-to-end concurrent complaint-submission verification.
