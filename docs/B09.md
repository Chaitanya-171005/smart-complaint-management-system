## Validation contract

Call `validate_evidence(files)` with the complete batch for ONE applicable
operation. Optional evidence permits zero files; four or more rejects the whole
batch before reading any bytes. Pass `request.FILES.getlist("evidence")` rather
than a single-item lookup that would silently discard additional files. Future
append/edit operations must include the retained count in their operation limit.

The validator reads actual bytes up to the configured maximum plus one, ignores
the declared size, restores upload cursors, and returns immutable snapshots.
Names must end in .jpg/.jpeg/.png/.pdf, case insensitive, and must agree with
parsed content. Client MIME is ignored; returned MIME comes from parsing.
JPEG/PNG use Pillow structure verification plus first-frame decoding. PDF uses
strict pypdf parsing and page-tree traversal; a magic header alone is insufficient.
Empty, damaged or encrypted PDFs are rejected because their content cannot be
verified. Filenames containing control/format characters are rejected and path
components are removed; original names are never storage keys or response names.
ValidationError provides a reason; callers must refuse the operation, not ignore
the invalid file and continue with the others.

This is content-format verification, not malware scanning, PDF sanitization or
a guarantee that every document renders correctly. Original bytes are retained.
Image decoding is capped at 25 million pixels as a processing safeguard, separate
from the SRS compressed-file byte limit. Review that safeguard with F4 before
final acceptance. Deployment still needs request-body limits, bounded parser
workers/resource isolation and an upload performance test; file-size limits
alone do not bound PDF parser CPU or memory.

## Private storage and transaction contract

`PrivateEvidenceStorage` is a Django storage backend rooted at
PRIVATE_EVIDENCE_ROOT (default: ignored `private-evidence/`). It has no `.url()`;
keys are generated UUIDs plus the verified canonical extension, independent of
user names. Files are created exclusively with mode 0600 and a new root with
mode 0700. Collisions do not overwrite existing bytes. Partial writes are removed
on an ordinary write exception.

Use `staged_evidence(files)` to validate the whole batch before any storage:

```python
from django.db import transaction
from complaints.evidence import staged_evidence

# Authorize the action FIRST. For intake use B04 can_submit_complaint; for
# resolution require the assigned resolver and F4's current-state checks.
with staged_evidence(request.FILES.getlist("evidence")) as stored:
    with transaction.atomic():
        # Recheck trusted master data/current state here.
        # Create Complaint, route it, and write required history as appropriate.
        # Persist each descriptor's storage_name, original_name, content_type,
        # size and sha256 against that SAME complaint. Stage/uploader/time are
        # server-controlled (anonymous uploader null), never accepted from POST.
        # F4 uses stage RESOLUTION; F2 uses INTAKE.
        pass  # Integration sketch only; no accepted complaint exists yet.
# Only acknowledge after this entire operation succeeds.
```

The context removes its newly stored batch if storage or the enclosed operation
raises, including database commit failure. Existing batches are untouched.
Keep the atomic block INSIDE the context, so commit failure is seen by cleanup.
Cleanup attempts every file, logs deletion errors and preserves the original
failure. A process crash or failed cleanup can leave an orphan: B10 needs a
persisted attachment/staging lifecycle and orphan reconciliation. This context
does not provide a distributed filesystem/database transaction or idempotency.
Do not wrap a successfully exited context in a later outer transaction that may
roll back; do not swallow failures inside it.

## Download contract for F2/F4

The future GET/HEAD-only view must load Attachment metadata by its identifier
from the database, including its own parent complaint (select_related where
appropriate), and pass it to:

```python
evidence_download_response(user=request.user, attachment=attachment)
```

Attachment must expose `complaint`, `storage_name`, `content_type`. Never build
it from GET/POST and never let the client supply a separate authorized complaint
alongside another attachment's storage key. The helper checks B04
can_view_evidence against THAT parent before opening storage. Missing and denied
attachments produce generic 404s. Readers are the active originating Complainant
or same-department Staff/Head; Admin, other users and anonymous references do not
grant access. Department readers may read an anonymous complaint's evidence.
Use the fresh authenticated request user on every request so role/membership
changes take effect. The upload action requires its own stronger action/state
permission; a reader is not automatically an uploader or resolver.

Only a generated flat key with a supported matching MIME is opened. Responses
force attachment download with a generated filename, verified MIME, nosniff,
private/no-store, Vary: Cookie and a sandbox content policy. There is no public
Django file-serving route. Do not add static(MEDIA_URL, ...), a web-server alias,
CDN/public bucket or staticfiles directory pointing at PRIVATE_EVIDENCE_ROOT.
Deployment must keep the volume private and persistent across restarts; the
absence of a Django URL alone does not secure a misconfigured reverse proxy.
