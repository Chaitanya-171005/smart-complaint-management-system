# B27 email attempts, retry scheduling and recovery

Issue #37; REQ-NOT-02 / TC-11. This builds on the uncommitted B21/B26 work
without replacing its event, authorization, privacy or business transaction
contracts. B28 UI is outside this change.

## Attempt budget and scheduling

The GitHub issue says “up to 3 retries”. The user's implementation instruction
is stricter: **at most three total attempts**, including the initial attempt.
This implementation follows that instruction: delays after attempts 1 and 2
are 60 and 300 seconds, measured from completion/recovery, persisted in
EmailDelivery.next_attempt_at. Equality at the due time is eligible. There is
no fourth reservation, inline retry loop or sleeping inside a business request.

EmailAttempt stores a unique (delivery, number), phase, start/lease/finish times
and static diagnostic code. Database constraints cap both the delivery count and
attempt numbers at three. Reserving before SMTP consumes the budget even if the
worker dies before sending: actual SMTP calls cannot exceed reserved attempts.

`python manage.py deliver_notifications --limit 100` processes due PENDING and
RETRY_WAIT jobs and expired SENDING claims. E03 must invoke it at least every
minute using cron/Jenkins/a worker scheduler against the same persistent DB as
the web app; deploy/notification-worker.cron.example is a reviewable example.
Schedules survive worker/process restarts. Repeated/overlapping invocations
recheck each row under its database lock; no process-local cache determines due
work. SMTP and retry processing never run inside a complaint transaction.

## SMTP outcomes and guarantees

| Outcome | Durable result |
| --- | --- |
| Exactly one message accepted by backend | SENT; no more attempts |
| Explicit temporary SMTP refusal (4xx), refused connection/DNS failure, or backend reports zero accepted messages | RETRY_WAIT until next due time; FAILED/attempt_limit after reservation 3 |
| Explicit permanent refusal (5xx), invalid address | FAILED immediately |
| Recipient no longer authorized/active/assigned | SUPPRESSED; no mail |
| Disconnect, timeout or arbitrary error that may follow SMTP acceptance | FAILED/delivery_unknown; UNKNOWN attempt, not automatically resent |

Failure classifications never retain SMTP response text, addresses, credentials,
session data, anonymous references, exception reprs or message bodies. Existing
B26 recipient authorization is checked on every attempt and immediately before
SMTP begins. Anonymous reporters still receive no email. Retry content retains
only the event's minimal ID/status projection; no new notification or history
event is created by a retry. In-app notices and committed complaint actions are
never rolled back or deleted by transport failures.

SMTP cannot provide exactly-once delivery across a lost acknowledgement or
process death. This policy retries only known non-acceptance. Uncertain outcomes
require operator investigation, sacrificing automatic resend rather than
creating an unbounded duplicate-send risk. Relay/provider behavior beyond its
SMTP responses is outside this guarantee. A permanent record can therefore mean
“outcome unknown”, not proof the recipient received nothing.

## Crash/restart protocol

1. Claim the delivery under a row lock, create CLAIMED attempt, persist a five
   minute lease and commit SENDING on the delivery before leaving the DB.
2. Re-lock and check the same attempt number/phase/lease and current recipient.
   Persist SENDING on the attempt and commit before calling SMTP.
3. Persist the outcome/schedule under the same delivery lock after SMTP returns.

An expired CLAIMED attempt becomes ABANDONED and schedules a bounded retry.
The previous owner cannot enter SMTP after that change: its attempt ID/number,
phase and lease must still pass the second transaction's fence. An expired
SENDING attempt becomes UNKNOWN, terminal on the delivery, and is never
automatically reassigned. This remains safe if the old process is paused rather
than dead. A late result from that same in-flight attempt may reconcile UNKNOWN
to its actual outcome; it cannot finalize a newer attempt.

A database failure after SMTP leaves the durable in-flight claim available to
the same conservative recovery. The command reports only sanitized errors and
continues its selected batch. Re-running it handles remaining due records;
there is no blind “reset SENDING to PENDING” operator command.

## Migration and deployment

0004_b27_email_attempts depends on unchanged 0003_b26_notifications. It adds the
attempt table, count, due timestamp and RETRY_WAIT status; no history, complaint
or notice is deleted. The data migration records old B26 SENT/FAILED outcomes,
preserves SUPPRESSED, leaves PENDING eligible, and quarantines legacy SENDING as
UNKNOWN. It does not resend previously sent or uncertain mail.

PR #68 still requires joining its independent history migration with this
branch's latest migration when integrated. No sibling migration is changed or
made an unavailable dependency. Tests compose that graph in a disposable copy.

Main currently configures console mail. Q02/E03 must configure the default
Django 6.1 MAILERS transport with environment-owned credentials, STARTTLS/SMTPS
and a bounded timeout (for example 30 seconds), plus worker invocation and
monitoring of FAILED/delivery_unknown records. No production credentials or
scheduler are installed by this implementation. The E03 Docker/Jenkins branch
remains separately owned; do not point tests at its deployed database.

## Verification scope

Deterministic tests exercise all three attempts, exact due boundaries,
increasing delays, success on each attempt, terminal/unknown results, stale
owner fencing, overlapping retry workers, permission changes, sanitized
records, legacy data migration and a child process actually exiting at both
durable crash boundaries. Synthetic localhost SMTP tests return zero, one,
two or three temporary refusals before acceptance/exhaustion; no external mail
is sent. The existing F2/F3 composition tests verify shared action/history
integration and anonymous-safe Head notices with the real outbox service.

Production PostgreSQL concurrency, SMTP TLS and deployed scheduler operation
require E03/Q02 verification. Local results are not proof of those environments.
The stricter three-total-attempt policy needs to remain explicit in peer review.
