## State and actor matrix (SRS §4.3)

Every pair not listed here is denied, including all self-loops and all outgoing
transitions from CLOSED or REJECTED. ESCALATED remains a flag, never a state.

| From | To | Permitted authority | Delivery in this change |
| --- | --- | --- | --- |
| SUBMITTED | ASSIGNED | Trusted system routing | Existing atomic F2/F3 intake; no account override |
| SUBMITTED | REJECTED | Admin or own-department Head | B20 core |
| ASSIGNED | IN_PROGRESS | Assigned same-department Staff or department Head | Shared B20 state primitive |
| ASSIGNED | REJECTED | Assigned same-department Staff or department Head | B20 core |
| IN_PROGRESS | RESOLVED | Assigned same-department Staff only | Policy present; B22 feature service required |
| RESOLVED | CLOSED | Originating Complainant/valid reference; expiry scheduler | Policy present; B23/B25 required |
| RESOLVED | REOPENED | Originating Complainant/valid reference | Policy present; B24 required |
| REOPENED | IN_PROGRESS | Assigned same-department Staff or department Head | Shared B20 state primitive |

F1 helpers own role/object permissions. Actor accounts are reloaded and locked
inside the operation; inactive, deleted, cross-department and unassigned Staff
cannot act. A Head may commence work but may not resolve it. Admin rejection is
limited to SUBMITTED, not ASSIGNED. Anonymous users/None are never implicitly
trusted System or reference principals. No caller-controlled system flag exists.

The Admin action does not confer complaint content/history/evidence access:
only the opaque revision and minimal TransitionResult are returned. There is no
new Admin read endpoint. The unresolved F1 discussion about an Admin rejection
screen/content view remains separate; no extra reading privilege is invented.

## Public account-action interfaces

`get_transition_revision(actor=..., complaint_id=..., target_state=...)` captures
an opaque 64-character revision only for a currently authorized matrix action.
This operation does not accept a caller's copy of a Complaint. It locks/reloads
the authoritative row and returns no title, description, reporter/reference or
other complaint content. The revision is a concurrency precondition, not an
authorization capability; every action independently rechecks current access.

`transition_complaint(actor=..., complaint_id=..., target_state=...,
expected_revision=..., reason="")` executes B20 core start/reject state changes.
It owns an atomic transaction (or savepoint within the caller's transaction),
locks Complaint then current actor, checks scope/revision/transition authority,
and saves only status. Existing department, assignee, due time, escalation and
other metadata are preserved. It records exactly one B21 event; B21/B26 create
required notices/outbox atomically. No SMTP is called. A caller's later failure
rolls back the same writes if it owns an outer transaction.

The return value contains only public complaint ID, previous/new state, history
ID and new revision, not an ORM Complaint object. Missing/non-visible records
produce 404; unauthorized actions on visible records produce PermissionDenied.
F1 refusal logging occurs after the service's rollback and contains no reason
input. An outer caller transaction still controls whether its security log
commits. State, history, notices and outbox remain unchanged on refusal/failure.

Terminal rejection requires a nonblank trimmed reason, with a technical maximum
of 2000 characters. SRS REQ-LIFE-01 requires a reason but specifies no terminal
rejection minimum. Its 20-character rejection minimum belongs to resolution
feedback (REQ-FDBK-02 / UC-08 / B24); it is not silently applied to REJECTED.
Optional commencement remarks obey the same input type/maximum bound.

## Revision/concurrency contract

The revision is a keyed SHA-256 digest of the full persisted Complaint row and
the count/maximum PK of its append-only history, not an exposed JSON snapshot.
Datetime serialization retains microseconds. This detects same-state F3
allocation/escalation, edits, and state/assignee ABA cycles. Count plus maximum
also catches a history append whose ID was reserved earlier but committed later.
Unrelated complaints' history does not invalidate a revision.

No F2 revision field or F3 increment contract is introduced. Existing F3 row locks
and history writes participate unchanged. An old token is rejected with
modified_record before another mutation can overwrite the current aggregate.
Current scope is checked first, so a revoked/non-visible actor receives denial
rather than learning state through a concurrency error. Changing SECRET_KEY or
the serialized model schema invalidates old revisions safely; clients refresh.

The service serializes supported state operations using the database row lock;
SQLite uses the repository's IMMEDIATE transaction setting. There is no hidden
lock-error retry loop. PostgreSQL lock behavior still requires deployment checks.
Direct ORM/SQL writes outside the shared service are not application access
interfaces and cannot be globally prevented by this service. Domain callers
must honor the shared aggregate lock/history boundary.

## Owner editing and later features

`validate_owner_edit(actor=..., complaint_id=...)` is a guard for a future edit
service. It requires an existing outer transaction, locks/reloads the Complaint,
and permits only its active Complainant while SUBMITTED. Every later state is
refused. It writes no fields and returns no content. The future edit service
must also implement its own editable-field validation/concurrency checks. No
existing post-submission edit endpoint exists or is enabled here.

Legal resolution/feedback/closure targets raise FeatureRequired from the generic
mutation API; they cannot bypass B22 remarks/evidence, B23 rating/confirmation,
B24 limits/SLA policy or B25 expiry checks. No resolution timestamp, rating,
reopen count, due time or auto-close policy is changed by B20. The shared start
primitive is not a completed B22 form/evidence/progress feature.

Reviewed future account feature services can reuse _account_transition for
locked scope/revision/matrix validation, perform ALL their business validation
and metadata writes inside that transaction, then use _apply_locked_transition
to save state/history. These private integration primitives are not view APIs
and accept no user-supplied callbacks or update dictionaries. The writer rechecks
state/actor policy. Reference feedback and scheduler actions require dedicated
checked capability boundaries; passing None is never sufficient authority.

## F2/F3 compatibility and verification

F2's existing atomic intake still creates SUBMITTED/ASSIGNED history and uses
its receipt/routing service, without routing it through an account action. PR
#68's optional actor/history keyword is reused when that model/API is present;
its schema/migration is not copied or duplicated. Lifecycle events then retain
the account actor in addition to actor kind. PR #70's flags/due/assignee contract
is unchanged, and terminal rejection causes its next run to exclude the record.

workflow/test_lifecycle.py covers all 49 pairs, core role combinations, deferred
feature gates, denial, reasons, current permissions, owner-edit guards, stale
replays/ABA/metadata changes, rollback, atomic notices and concurrent actions.
integration_checks/lifecycle_f3.py explicitly requires #68/#70 sources and tests
actual allocation/escalation revision invalidation, rollback and concurrency.
Missing integration dependencies fail, never skip. These tests run in a
disposable source composition with a temporary migration join; no Git merge is
performed. Full B20 acceptance through B22-B25 UI/actions remains dependent on
those features, team review and delivery evidence; it is not claimed here.
