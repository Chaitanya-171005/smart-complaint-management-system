# Q04 measurement runner and deployment handoff

Owner: Atul Suresh. Related to issue #20, TC-15 and NFR-PERF-01/02/03.
This change prepares measurement infrastructure. It supplies no deployed
performance result and does not close Q04. The Actions job tests the runner and
application regressions; that job is not a 50-user deployment benchmark.

## Acceptance inventory

| Required check | Limit | This runner |
| --- | --- | --- |
| Intake, list, detail, valid reference tracking with 50 users | p95 <= 2,000 ms each | Configurable HTTP scenarios; actual deployment required |
| Queue and successful business action with 50 users | p95 <= 1,500 ms each | Configurable HTTP scenarios; prepared targets required |
| Applicable list/queue pagination | <= 25 records/page | Explicit per-record match and page-boundary scenarios; other lists still need owner inventory |
| Escalation of 5,000 eligible complaints | <= 60 seconds | Separate F3 management-command measurement remains pending |
| Representative 12-month report | <= 5 seconds | Separate F4 report measurement remains pending |
| Agreed 5 MB upload, shaped to 2 Mbps | <= 30 seconds | Separate actual upload/network-shaping measurement remains pending; D02 unresolved |

F3/E03 supplies an authorized disposable Docker/PostgreSQL deployment, exact
build revision, worker/resource configuration and persistent volumes. F1/F3/F4
supply active synthetic reference data, test records and valid accounts. Record
schema/data sizes, host resources, app workers, network topology, ingress limits
and database settings alongside the report. Results from local SQLite or a mock
HTTP server do not establish deployed PostgreSQL acceptance.

## Configure outside the repository

Copy `q04.example.json` to a private working directory outside the checkout.
All example scenarios are deliberately disabled. The list/detail placeholders
must be replaced with routes from the deployed F4 revision. B15 queue/action
and B13 tracking must be deployed and owner-approved before their cases run.
Do not enable anonymous release or weaken its privacy/transport/limiter checks
merely to produce benchmark results. The runner changes no application settings.

Set the environment metadata to the actual deployed 40-character Git revision,
`postgresql` or `sqlite`, representative dataset description and actual network
conditions. Record additional machine/database details in the final evidence
handoff. Set `SCMS_Q04_BASE_URL` to the deployment origin (scheme, host and port;
no path, credentials or query). Default TLS certificate verification is retained.
No redirects are followed, so login redirects cannot silently become fast 200s.

For each case set `enabled: true`, the actual path/method and the exact expected
success status and a response pattern specific to the accepted operation or
known test complaint. Never use a generic HTML/title, login page, validation
error or tracking no-match page as the success marker. A redirect-success pattern
matches Location; it must point to the expected application route, not login.
Pagination patterns must match exactly once per complaint row; validate the
pattern against a representative full page and page 2. List/queue must declare
that check for the combined HTTP result to pass. Add other pages in separate
config runs and keep their evidence; this does not discover every list in F4.

Authenticated cases require 50 distinct preauthenticated test accounts of the
configured role. An actor JSON file outside Git has this shape:

```json
{
  "COMPLAINANT": [
    {"account_key": "synthetic-complainant-01", "session_cookie": "LOCAL-SECRET-DO-NOT-COMMIT"}
  ],
  "HEAD": [
    {"account_key": "synthetic-head-01", "session_cookie": "LOCAL-SECRET-DO-NOT-COMMIT"}
  ]
}
```

The example shows one entry only; each exercised authenticated role needs 50
unique account keys AND session cookies. Owners must confirm these really are
distinct authorized accounts. Obtain sessions through the real login flow before
timing and keep the actor file private (mode 0600). Credentials, cookies and raw
references must never be committed or included in shared evidence. The runner
uses one cookie jar per actor; it does not fetch login credentials from Git.

Intake prepares a fresh form/CSRF token before EVERY POST and rejects repeated
operation tokens. Configure category/location through `SCMS_Q04_CATEGORY` and
`SCMS_Q04_LOCATION`, referring to active synthetic data. Every preflight/measured
POST creates a separate synthetic complaint. No email/contact policy is invented.

Action cases additionally require an `operations.action` array on each actor,
with one distinct valid business target for warmup plus each measured iteration:

```json
{
  "target_key": "synthetic-complaint-unique-for-this-operation",
  "path": "/complaints/SCMS-2026-000001/assign/",
  "prepare_path": "/routing/queue/",
  "payload": {"assignee": "DEPLOYED-ELIGIBLE-STAFF-ID", "expected_assignee": "", "reason": "Synthetic load test"}
}
```

This is a shape example, not a real complaint/staff identifier. Owners provision
one independently actionable complaint per operation and verify the expected
initial state/department/assignee. Reusing an already completed action or stale
assignment is not a valid action-latency measurement. Config/manifest files stay
outside Git. Include all warmup records in the dataset inventory.

For valid tracking set `SCMS_Q04_REFERENCE` locally; it is posted in the body,
never the URL/report. Fifty clients from one network source can legitimately hit
the B13 limit. Coordinate real permitted test sources with E03 and record NAT
behavior; do not bypass/reset the limiter to claim a pass. The optional
`ANONYMOUS` actor array can contain one `{ "source_address": "OWNED-LOCAL-IP" }`
entry per worker. These are real socket source-address bindings, not forged
X-Real-IP/X-Forwarded-For headers; E03 must provision those addresses/interfaces
and verify the ingress sees distinct permitted source buckets. Authenticated
actors may also carry this optional field. NAT and IPv6 /64 grouping still apply;
multiple local addresses do not guarantee distinct buckets after the ingress.
Keep the ten-attempt window intact: the example tracking case uses 9 measured
iterations plus one warmup per source, for 450 measured tracking samples. Do not
rerun inside the same window and reinterpret throttling as successful lookups. Test deliberate 429s
separately from valid-lookup p95. An unavailable backend, cold-start quarantine,
503 or no-match response makes the valid-lookup benchmark incomplete/failed.

## Run and interpret

With the deployment/configuration/accounts ready, run from the project root:

```sh
python scripts/q04_load.py \
  --config /absolute/private/q04.json \
  --actors /absolute/private/actors.json \
  --output build/evidence/q04-run-UNIQUE/report.json
```

Use a new output path for every run; existing evidence is never overwritten.
The base URL and payload environment variables must be set in that terminal;
never paste real session cookies/references into shared shell transcripts.

The CLI enforces 50 concurrent logical users and 1–100 measured iterations per
user, default 10. Each user performs one validated untimed warmup operation, then
all measured workers start behind a barrier. Requests are closed-loop, without
think time, using urllib HTTP/1.1 connections rather than browser rendering.
Connections/TLS setup are included in measured request latency; there is no
browser persistent connection pool. Record this load model with results.

POST measurements time the submitted request through response-body receipt.
Fresh-form preparation is additional concurrent traffic outside the POST timer;
prepare failures still prevent a pass. Failure timings are retained, not filtered
out. Percentiles use nearest rank; 50 users x 10 iterations gives 500 samples per
scenario (450 for the tracking override). p95 alone is insufficient: every sampled operation must also satisfy
status/content checks. An operator must independently verify accepted database
operations after a mutation run; response validation does not prove durability.

Reports include only run/environment metadata, numeric timings/status codes,
scenario names and fixed error categories. They omit paths, request/response
bodies, operation tokens, actors and cookie/header values. The target origin is
represented by its hash. Keep dataset descriptions free of private information.

Exit 2 / BLOCKED means required environment or test inputs are missing. Exit 2 /
INCOMPLETE_OR_FAILED means scenarios failed or required cases/pagination checks
are missing. Exit 0 / HTTP_CHECKS_PASS covers only the six HTTP cases plus their
configured list/queue pagination. It is never a full Q04 PASS: escalation, reports,
real network-shaped upload and any other applicable lists remain explicitly
pending. Record failed targets as defects, then rerun after fixes on new evidence
paths; do not relabel failures, skipped cases or disabled scenarios as passes.

## Regression verification

`python -m pytest test_q04_load.py --no-cov -q` tests real loopback HTTP behavior,
CSRF/fresh-token handling, rejected redirects/no-match/errors, pagination limits,
actor/target requirements, percentile math, incomplete coverage and redacted
reports. These validate the harness; their timings are not deployment evidence.
Run the project's full `scripts/ci_checks.sh` checks before review. Chaitanya is
the reviewer for Atul's Q04 infrastructure PR. Issue #20 remains open.
