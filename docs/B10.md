## Delivered scope

This contribution adds a persistent authenticated retry receipt and a guard
around a trusted required-operation adapter. The receipt, identifier reservation
and callback database writes commit together. Identical retries return the
original identifier/time without repeating the operation or notification hook.
Changed data with an already accepted key is refused.

The authenticated aggregate adapter now lives in `complaints.submission` and
connects the merged B07/B08/B09/B14/B16 helpers to real Complaint/Attachment
records and the existing B21 history writer. Its contract, migration and limits
are documented in [B10_INTEGRATION.md](B10_INTEGRATION.md). The existing guard
tests retain their synthetic callbacks; separate `test_submission.py` cases
exercise real aggregate persistence, cleanup, replay and required failures.
The authenticated HTTP flow is implemented in [B07_HTTP.md](B07_HTTP.md) and
remains disabled by default until D01 is confirmed. Durable notification/staging
recovery and deployment acceptance remain pending. Issue #15 stays open.

## Authenticated request contract

`new_intake_key()` creates a 256-bit random key for one authenticated form
operation. The POST form retains that key in a signed, account-bound token when retrying the same
submission after a timeout. A newly started submission gets a new key.
`key`, `payload_digest` and each item in `evidence_sha256` must be strings of
exactly 64 lowercase hexadecimal characters (`[0-9a-f]{64}`).

For an authenticated caller, an invalid key format raises
`ValidationError(code="request_key")`. An invalid `payload_digest` raises
`ValueError`. `submission_digest()` raises `ValueError` if `fields` is not a
dictionary or an evidence hash has an invalid type or format. Evidence hash
iterables must be iterable; supplying a non-iterable raises `TypeError`.

`execute_intake()` checks key format and scopes receipts to the authenticated
account. It does not verify that the server previously issued the key. If the
HTTP adapter requires proof of issuance, it must enforce that separately. The
current authenticated view uses Django signing and validates the bound account.
The adapter must provide authentication and CSRF protection. B11/B12 must define
an anonymous retry scope without a submitting account.

Use `submission_digest(fields=..., evidence_sha256=...)` on server-canonical
submission data. Include ALL submission-affecting values, including stable
category/location keys, validated B07 fields and persisted attachment metadata
such as original names, verified MIME and stage where relevant. Include ordered
SHA-256 hashes of the actual validated file bytes. File order is significant.
Compute `payload_digest` on the server from those values.

The `fields` dictionary may contain JSON-compatible strings, booleans, integers,
finite floats, `None`, lists/tuples and nested dictionaries. Convert `Decimal`
and `datetime` values to agreed canonical strings before calling the helper.
Unconverted values raise `TypeError` during JSON serialization. Non-finite
floats raise `ValueError`.

Use string dictionary keys throughout the adapter's canonical representation.
The helper currently accepts JSON-supported non-string keys and coerces them to
strings. Consequently, `{1: "x"}` and `{"1": "x"}` produce the same digest.
Tuples and lists also serialize identically, so `{"x": (1, 2)}` and
`{"x": [1, 2]}` produce the same digest. Mixed-type dictionary keys can raise
`TypeError` when sorted. Canonical input types must be consistent across an
original submission and retries so distinct accepted submissions cannot collapse
to the same representation.

Normalize Unicode strings, including dictionary keys, consistently (for example,
using NFC) BEFORE validation and storage. Hash the same normalized values that
are validated and persisted. Apply that sequence to an original submission and
every retry. `submission_digest()` sorts keys and serializes values; Unicode
normalization, B07 validation and option-to-key mapping belong to the adapter.

Only a SHA-256 key digest and payload digest are stored in the receipt, alongside
the authenticated user, original ID/time and creation time. Receipt uniqueness
is enforced for (user, key_digest), and complaint_id is unique. Receipts are
internal and not registered in admin. Do not edit/delete accepted receipts or
expire their keys independently of the future complaint's retry policy, because
that could permit a duplicate after an old response timeout. Final retention and
a legacy-receipt reconciliation policy remain tracked in #15.

The nullable `accepted_complaint` relation uses `to_field="complaint_id"` and a
database constraint requires its identifier to equal the retained external ID.
Migration 0004 links exact identifier/account/time matches and preserves all
unmatched receipts without inventing Complaint records. Generic legacy callbacks
remain compatible. The new service uses `require_complaint=True`: it requires a
matching persisted Complaint on acceptance and refuses unlinked/mismatched legacy
replays with `IntakeReconciliationRequired(code="intake_reconciliation")`.

## Transaction and failure boundary

`execute_intake(user=..., key=..., payload_digest=..., operation=...,
staging=None, after_commit=None)` owns the OUTERMOST default-database
transaction. It refuses nesting, so it cannot return acceptance while another
outer transaction could still roll back. An eventual ATOMIC_REQUESTS view must
use Django's non_atomic_requests for this service boundary. Default Main does
not enable ATOMIC_REQUESTS.

The current user is fetched and authorized through B04 BEFORE file staging.
The account row is locked and its current active role rechecked inside the
transaction before receipt lookup. A refusal remains a refusal even for an
existing receipt; possession of a key never grants record or evidence access.
The role/active state recheck also catches a change during slow staging.
Authorization refusal logging happens outside rollback so the audit survives.

Intake is serialized per account, including different keys. Main's configured
SQLite IMMEDIATE mode serializes writers before reads; the account row lock is
also expressed for a future row-locking database. Concurrency is tested on
file-backed SQLite only. PostgreSQL behavior and throughput remain unverified;
do not claim production multi-database or performance acceptance. There are no
hidden lock retries. A retryable database failure must retry the WHOLE operation
with its original key after rollback, not only allocation or one sub-operation.

For a new key, the guard obtains a server timestamp and reserves the B08 ID,
then calls `operation(IntakeContext)` with the fresh User, provisional ID/time,
and staged evidence descriptors. The required adapter must recheck master data,
create the real Complaint, perform B14 routing/B16 priority/due-time work, persist
Attachment metadata, and write required initial history in this SAME default
database transaction. It must raise on any required failure, not silently
ignore it. It must not commit, send mail, publish acceptance or write to another
database. No receipt is written until that adapter succeeds; a later receipt
write or database commit failure rolls back the ID and all required DB writes.
No incomplete PENDING receipt is committed by the guard.

Only after the transaction commits does the service return IntakeResult.
An identical receipt replay returns `replayed=True` and the original time/ID,
even across reconnection or year rollover. Reusing an accepted key with a
different digest raises IdempotencyConflict. The authenticated view presents
HTTP 409, never acceptance of the changed data.
Other validation, permission, storage and database exceptions also propagate;
the HTTP view must not turn them into a success page.

## B09 staging and required cleanup

The aggregate service handles this wiring. Other trusted adapters can pass
B09's context manager as a callable, for example:

```python
# Generic-adapter sketch, not an installed endpoint. The real authenticated
# caller normally uses submit_authenticated_complaint instead.
result = execute_intake(
    user=request.user,
    key=server_issued_form_key,
    payload_digest=server_digest,
    staging=lambda: staged_evidence(request.FILES.getlist("evidence")),
    operation=persist_complete_intake,
    after_commit=enqueue_notification,
)
```

The staging context encloses the guard's transaction; it must clean this
attempt's new files on ANY escaping exception and retain them on success.
The operation gets descriptors through `context.evidence`. Failures, including
database commit failure, unwind the staging context for cleanup. A replay also
unwinds its NEW batch with an internal signal before returning the existing
receipt, so re-uploaded retries do not leak duplicate files. The already
accepted original files are not touched. Do not catch/suppress exceptions inside
the staging context. For retries with evidence, do NOT independently wrap a
normally returning replay in staged_evidence: that would retain unused files.

B09 handles ordinary write/cleanup exceptions; neither module makes filesystem
and DB commits atomic against a process crash. A crash between staging and DB
commit or a failed deletion can leave an orphan. B10 still needs durable staging
metadata, orphan reconciliation and restart/recovery tests against actual
Complaint/Attachment records. Replays after a crash also need that real linkage.

## Mail and notifications

`after_commit(IntakeResult)` is registered only for new successful operations,
using Django's robust on_commit hook. It runs after commit; an ordinary callback
exception is logged and cannot reverse business acceptance or escape as an
intake failure. A replay does not send the hook again. This is NOT a durable
notification outbox: a process crash after commit but before the hook can lose
delivery. B21 must persist and dispatch required notification jobs reliably.
