# B11/B12 complaint schema and anonymous reference contract

Owner is Atul Suresh, F2. Related issues are #16 and #17. This schema contribution
is reviewed in PR #62 against SRS Appendix B-2 and the B04 permission contract.

The anonymous service/HTTP flow is now implemented in `anonymous.py` and
`anonymous_views.py`, building on PR #69. See B11_ANONYMOUS.md for the complete
transaction/one-time-response contract and B12_PRIVACY.md for the privacy audit
and deployment prerequisites. Anonymous release remains disabled by default.

## Persisted fields and ownership

| Data | Schema supplied by PR #62 | Writer/integration owner |
| --- | --- | --- |
| Identifier and submitter | Unique `complaint_id`, nullable `submitted_by` | F2 B08/B10 intake |
| Category | Stable `category_key`, submitted label snapshot in `category` | F2 consumes F3 B17 category keys |
| Location | Canonical `location_code`, `block`/`floor`/`room_area` snapshots | F2 consumes F1 reference data |
| Submitted content | `sub_category`, `title`, `description`, `priority` | F2 B07 validation, F3 B16 effective priority |
| Routing | `department`, nullable `assignee`, `unrouted`, `routing_rule_key` | F3 B14 PR #60 and B15 issue #23 |
| Escalation | `is_escalated`, `escalation_level` | F3 B18 issue #26 |
| Lifecycle | `status`, `reopen_count`, `resolution_remarks`, `rating`, `resolved_at`, `closed_at` | F4 B22 issue #32, B23 #33, B24 #34, B25 #35 |
| Times | `submitted_at`, `due_at` | F2 intake and F3 B16 |
| Anonymous reference | Unique nullable `reference_digest` | F2 B11/B12 |

The listed columns are included here so those integrations can update existing
fields. F3/F4 owners must confirm the adapter mappings before wiring their
services. Their routing, escalation and lifecycle behaviours remain separate
feature work. `unrouted=None` denotes an outstanding routing decision. A completed
decision sets it to true for fallback or false for a rule. The stored rule key is
exactly `routing_rule_key = str(rule.pk)`. A rule's `scope_key` is derived from its
editable scope and must never be used as this historical identifier. A pending
decision or fallback has an empty rule key; a rule decision has a nonempty key.
Database constraints enforce these combinations, including the pending/null case.
Update both fields together when persisting a decision. Stored decisions remain
authoritative after later configuration changes.

B10 PR #67 supplies the production adapter integration. Both adapters share
the required persistence routine, call B14 `route_and_prioritize()` and use
`RoutingOutcome.as_complaint_fields()` to set department, unrouted, rule key,
effective priority, due time and `ASSIGNED` status (REQ-ROUTE-01).
Routing and these Complaint updates must occur in the same intake transaction;
a failure must roll back the entire operation.

The `category` label is a historical snapshot. Reports should group by
`category_key`, defined as exactly `str(category.pk)`. The key is required,
non-null and a positive decimal primary-key string; the database rejects omitted,
empty and malformed keys. Renaming a category must not rewrite earlier snapshots
or infer a key from a label. Intake resolves the current Category row, verifies
that it is active, and stores its primary-key string with the label snapshot.

The model/form priority copies are covered by a contract test. B17 is merged;
the second contract directly imports `routing.models.Priority` and always runs.
Adding or reordering a priority requires updating all shared contracts before
feature integration. F3 confirmed under B16/#24 that only the effective
priority is persisted, alongside `due_at`, as required by REQ-SLA-01, BR-05 and
SRS Appendix B-2. No separate user-indicated-priority column is required.
The authenticated intake adapter includes user-indicated priority in its
canonical retry digest. The anonymous adapter preserves that rule too.

The database requires `is_escalated == (escalation_level > 0)`. Writers must update
the flag and level together within their business transaction.

## Reference generation and storage

For a new anonymous Complaint, the trusted intake caller invokes
`issue_anonymous_reference()` once before persistence. It generates 16 random
bytes through `secrets.token_hex(16)`, returning 32 lowercase hexadecimal
characters with 128 bits of entropy. It stores only the SHA-256 digest. The
method rejects authenticated complaints and repeated issuance. It calls
`complaints.references.hash_reference()` and does not add the raw reference to
the model instance or database fields. B13 lookup must reuse that helper. The
helper accepts exactly 32 lowercase hexadecimal characters and raises ValueError
otherwise; the eventual lookup must map that error to its generic no-match
response without logging the submitted reference.

Unsalted SHA-256 here relies on that high-entropy source. Never substitute a
human password, complaint ID, account value or predictable counter. A focused
test verifies the secrets call with 16 bytes and the resulting digest. The
database rejects uppercase, non-hex, short and duplicate reference digests.

The caller must retain the raw reference only long enough to display it after
the full intake transaction commits, with a warning that it cannot be recovered.
It must not log it or place it in URLs, notifications or persistent sessions.
The HTTP response has private/no-store, no-referrer and noindex controls. Only a
newly committed operation returns the raw reference. Accepted retries return no
reference; the service never persists a recoverable copy. Tests cover concurrent
double submission, response replay and required-operation failures.

## Schema constraints and migration

An authenticated record has a submitter and no reference digest. An anonymous
record has no submitter and exactly one valid digest. Identifier format and
uniqueness, digest uniqueness, rating range and text length limits are enforced
by database constraints, including on SQLite. Length validation applies before
storage through B07/model validation too. Department queue and owner list
indexes cover `(department, status, due_at)` and `(submitted_by, submitted_at)`.

Merged migration `0003_complaint` creates the reviewed Complaint schema and
constraints. It is not rewritten by the anonymous feature. The new additive
`0005_anonymous_intake_receipt` creates only anonymous-operation deduplication
receipts, without account/session/source fields. Apply migrations normally;
no rollback, reset, fake state or data deletion is required.

IntakeReceipt retains its external identifier and now has a nullable
`accepted_complaint` relation to the same Complaint identifier. B10 migration 0004
links only matching identifier/account/submission-time triples. Unmatched legacy
rows remain intact and unlinked; the authenticated aggregate service refuses to
acknowledge them until explicitly reconciled. See B10.md and B10_INTEGRATION.md.

## Privacy boundary and remaining verification

The schema stores no anonymous account, name, email or client-IP field. Real
Complaint permission tests verify owner access and refusal of full-record and
evidence access to anonymous callers and unrelated complainants. A reference
alone does not grant evidence access.

User-entered free text and evidence can still contain identifying information.
The schema constraint cannot establish their anonymity. B12_PRIVACY.md records
the implemented metadata/session/error/logging safeguards, safe output contract,
current-surface tests and remaining owner/deployment verification. Tracking
throttling metadata must remain transient and unlinked to a Complaint; B13 lookup
is a separate feature and is not enabled by the anonymous submission page.
