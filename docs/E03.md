# E03: Jenkins, Docker deployment and persistence

Issue #27. This guide covers the repository's Docker/PostgreSQL deployment,
Jenkins verification pipeline and gated deployment handoff. A Jenkinsfile or a
successful local test run is not evidence that Jenkins or production deployment
has actually executed.

## Local database configuration

SQLite remains the default (`DJANGO_DB_ENGINE=sqlite`). `DJANGO_DB_PATH`
optionally selects its database file; tests use a separate file. SQLite uses
IMMEDIATE transactions with a 20-second timeout. PostgreSQL is selected with
`DJANGO_DB_ENGINE=postgresql` and `DJANGO_DB_NAME`, `DJANGO_DB_USER`,
`DJANGO_DB_PASSWORD`, and `DJANGO_DB_HOST`; `DJANGO_DB_PORT` defaults to 5432.
The password is required and must not be committed. Psycopg is pinned in
`requirements.txt`.

Run Django against a temporary/test database for checks. Do not point test
commands at a persistent deployment database. PostgreSQL concurrency and
locking acceptance must be performed against a separately provisioned,
disposable PostgreSQL service.

## Docker setup

Install Docker Engine/Desktop with the Compose v2 plugin. Create a private
deployment environment file from `.env.docker.example` (never commit the
resulting `.env.docker`) and set the secret/database/allowed-host values. Start
the stack with:

```sh
docker compose --env-file .env.docker up -d --build --wait
docker compose --env-file .env.docker ps
```

Compose waits for PostgreSQL's `pg_isready` health check before starting the
application. The entrypoint applies migrations before executing Gunicorn. The
application image runs as the unprivileged `appuser`; its health check requests
the login page. The database is not published on a host port. PostgreSQL data
uses `postgres_data`; private evidence uses `private_evidence` mounted at
`/data/private-evidence`. Evidence is not exposed as a static/media URL. Both
services use restart policies.

SQLite remains supported for development and tests. Docker Compose explicitly
selects PostgreSQL. `SCMS_IMAGE` optionally overrides the image reference for
CI deployment; local builds default to `scms-app:local`.

Create the initial administrator interactively:

```sh
docker compose --env-file .env.docker exec app python manage.py createsuperuser
```

## Anonymous intake and Q02 security gates

Compose forwards the intake and transport settings from environment with
closed defaults. `COMPLAINT_INTAKE_ENABLED`, `ANONYMOUS_INTAKE_ENABLED`,
`ANONYMOUS_PRIVACY_READY`, and `ANONYMOUS_TRANSPORT_VERIFIED` default to
`False`; HTTPS mode is blank, secure cookies/redirect are false, and HSTS is
zero. Keep them that way until the Q02 owner verifies the actual TLS topology,
reverse-proxy header overwrite and backend isolation, cookie behavior, HSTS,
privacy controls and deployment logging. Do not infer proxy trust from a
configuration flag or enable anonymous release as part of an E03 deployment.
See [B11 anonymous deployment prerequisites](B11_ANONYMOUS.md) and issue #28.

## Jenkins installation and credentials

Use a Jenkins multibranch Pipeline job for this repository, with `Main` as the
protected production branch. The agent label is `docker-python`; provide a
supported Python matching the pinned requirements, Docker CLI/Compose v2, and
permission to use the Docker daemon. Install Jenkins Pipeline, Credentials,
SSH Agent, and Credentials Binding plugins. Configure the branch protection and
Jenkins authorization so only the designated deployment approvers can proceed
through the production input gate.

Configure the multibranch source to use the target branch's trusted Jenkinsfile
for untrusted pull requests (including same-repository branches), and do not
bind deployment credentials to any job that executes an untrusted branch's
Jenkinsfile. Restrict credential folder/job scope to the protected production
job. If this trust separation cannot be guaranteed by the installed GitHub
Branch Source configuration, use a separate deployment job whose pipeline
definition is pinned to protected `Main`; repository-side `when` conditions
alone are not a security boundary against a modified Jenkinsfile.

Create these Jenkins credentials (the IDs are referenced by `Jenkinsfile`):

| Credential ID | Type | Purpose |
| --- | --- | --- |
| `scms-registry-push` | Username/password | Push the immutable build image |
| `scms-deploy-ssh` | SSH private key | Connect to the configured deployment host |
| `scms-deploy-known-hosts` | Secret file | Pinned SSH host key(s), verified out of band |

Set the non-secret Jenkins environment values `SCMS_IMAGE_REPOSITORY`,
`SCMS_REGISTRY_HOST`, `SCMS_DEPLOY_HOST`, and `SCMS_DEPLOY_DIR` in the protected
job configuration. `SCMS_DEPLOY_DIR` must name a pre-provisioned directory on
the deployment host containing its own protected `.env.docker` file and Compose
configuration. The deployment host must already be authenticated to pull from
the registry. Do not copy deployment secrets through build logs or command-line
arguments. Do not use `ssh-keyscan` at deploy time; supply a verified known-hosts
file.

The pipeline installs pinned Bandit 1.9.4 (Python 3.14 compatible) and
pip-audit 2.9.0, runs compile/static and
dependency security checks, invokes `scripts/ci_checks.sh` for Django checks,
migrations, the complete test suite and coverage gate, then builds the image
once and runs `manage.py check` inside that exact image. Any failed stage stops
later stages. CI creates a throwaway Django key in the agent shell; Jenkins
secrets are not exposed to pull-request or feature-branch code when the Jenkins
trust and credential scoping above are configured. Deployment is
additionally disabled by default, limited to the protected `Main` branch (not a
change-request build), and pauses for the configured human approval. It pushes
the already-built image, extracts the registry digest, and deploys the immutable
`repository@sha256:...` reference with `--no-build --wait`. The digest is
printed in the Jenkins log for release traceability. It does not rebuild or run
database-volume removal/`docker compose down -v`.

To execute the shared checks manually in a clean checkout, install
`requirements-dev.txt`, install `bandit` and `pip-audit`, and export a
throwaway `DJANGO_SECRET_KEY` in the shell. Then run:

```sh
python -m pip install -r requirements.txt -r requirements-dev.txt bandit==1.9.4 pip-audit==2.9.0
python -m compileall -q accounts complaints routing workflow scms manage.py scripts
python -m bandit -q -r accounts complaints routing workflow scms manage.py scripts -x "**/test_*.py,**/tests.py,scripts/q04_load.py"
python -m pip_audit -r requirements.txt -r requirements-dev.txt
sh scripts/ci_checks.sh build/evidence/manual-<unique-run-id>
```

Bandit scans application and migration Python under the five Django packages,
`manage.py`, and the shared CI scripts. It excludes test modules (`test_*.py`
and `tests.py`) and the Q04 load-test harness `scripts/q04_load.py`; these
contain assertions, synthetic credentials, or test-only subprocesses and are
not runtime application/CI code. `.dockerignore` excludes those modules,
`conftest.py`, `integration_checks/`, and the Q04 harness from the production
image, so every Python file copied into the image is within the Bandit scan.
The separate `integration_checks/` directory
contains only manual integration-test harnesses, while `docs/evidence/`
contains archived verification helpers and generated evidence; neither is
deployed application or CI source. Virtual environments and generated build
artifacts are also outside the scan. The broad diagnostic scan reports Bandit
warnings in those manual harnesses, including XML parsing of locally generated
JUnit output; they are not on a deployment or request path and are not hidden
by the production scan. Review the harnesses separately if they are adapted to
consume untrusted XML.

The two `TOKEN_SALT` constants in the authenticated and anonymous intake views
are public Django signing namespaces, not credentials. Django documents that
salts separate signature namespaces; signature integrity depends on
`SECRET_KEY`. Each exact assignment has a `# nosec B105` annotation with a
reason immediately above it. There is no global B105 skip or altered severity
or confidence policy. `scripts/run_tests.py` has equally narrow B404/B603
annotations because its subprocess executes only fixed, repository-controlled
Python argv lists without a shell; the command is not derived from user input.

Use a new evidence directory for each run. Jenkins archives its CI evidence
under `build/evidence/jenkins/<BUILD_NUMBER>`. Evidence reflects only commands
that actually ran; local results do not claim a Jenkins build or deployment.

## Persistence verification and safe replacement

For a disposable end-to-end check, first confirm Docker is available, then run:

```sh
sh scripts/verify_docker_persistence.sh
```

The script creates a unique Compose project, temporary credentials and
project-scoped database/evidence volumes. It writes synthetic markers, forces
replacement of both containers, and verifies both markers remain. Its cleanup
removes only that run's uniquely named disposable project and volumes. Never
run `down --volumes` against a deployment project.

An actual Docker Desktop run is recorded in
[`docker-persistence.log`](evidence/e03-docker-persistence/docker-persistence.log).
The log shows a successful image build, healthy Django/PostgreSQL containers,
recreation of both containers, and the final persistence-success message. This
is genuine Docker persistence evidence. The operator reports that the
disposable containers and volumes were cleaned up, but the log does not include
the cleanup command's output, so that detail is not independently confirmed by
this artifact. This Docker run is not Jenkins or production deployment evidence.

For ordinary deployment replacement, preserve the Compose project name and
volume names. Use `docker compose pull` followed by `docker compose up -d
--no-build --wait`; do not use `down -v`, `volume prune`, or change the project
name, since Compose project names namespace volumes. Before production changes,
confirm backups and a tested restore procedure with the deployment owner.

## Rollback

Keep the prior image digest and a database backup before deployment. To
roll back application code, set `SCMS_IMAGE` to the previous immutable image
and run `docker compose --env-file .env.docker up -d --no-build --wait app` in
the same project directory. This keeps PostgreSQL/evidence volumes intact.
Application rollback does not reverse database migrations. Only use a database
restore or forward-fix plan approved by the database owner; do not delete or
reset volumes as a rollback shortcut.

## Verification status and limitations

Repository tests assert the Dockerfile's non-root user and health check, Compose
PostgreSQL readiness, volume mounts, restart policy, disabled privacy defaults,
and the scoped persistence probe. Jenkinsfile tests assert stage ordering,
security gates, credentials references and deployment conditions; they do not
execute Jenkins' Groovy pipeline engine. The full suite and Docker-configuration
tests must be rerun after changes.

Local validation on Python 3.14.6 passed the scoped Bandit 1.9.4 scan and
pip-audit 2.9.0 with no known vulnerabilities, plus all 1,170 tests and the
coverage gate (96.14% overall). The module gates passed. The exact commands,
exit codes, and dirty-source metadata are recorded in
[`e03-jenkins-local-validation`](evidence/e03-jenkins-local-validation/summary.md).
These are local results, not a Jenkins build.

Local Jenkins build 6 executed the pipeline successfully with deployment
disabled: 1,170 tests passed, coverage was 96.14%, all coverage gates passed,
and the isolated Docker image built and passed its Django check. The build
checked out `f300552` and applied uncommitted Jenkinsfile and test fixes; its
workspace also contained an untracked copy of the original Jenkinsfile. See
[`e03-jenkins-build-6`](evidence/e03-jenkins-build-6/summary.json) for source
state and sanitized stage evidence. This does not verify a clean commit or a
production Jenkins configuration. Docker persistence was executed as recorded
above. Production PostgreSQL, registry,
SSH deployment, backup/restore, TLS/proxy, cookies, HSTS and anonymous privacy
acceptance remain separate environment checks. Q02 issue #28 owns production
transport security; E03 must not bypass its review.
